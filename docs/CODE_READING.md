# AimFind 取码方案（驿站取件码，例：B2-4-2073、C5-5-7225）

> 需求已从"通用目标检测"收敛为**读一串固定语法的码**。本文给出从零训练到必须训练的完整分档路线、
> 每档的判据与验收指标。**先做 §0 的三问，再决定投入哪一档** —— 多数团队在这里省掉了一次训练。

---

## 0. 先定三件事（决定整条路线）

| # | 问题 | 分支后果 |
|---|---|---|
| 1 | **载体是什么？** 印刷文本 / 条码·二维码 / 点阵喷码 / 手写贴牌 / 曲面标签 | 若是**条码或二维码** → 整方案塌缩成 L0，半天结束，别做任何图像识别 |
| 2 | **码表能否枚举？** 合法码是有限集合（几千~几万条）还是无穷文法 | 能枚举 → **白名单最近邻**（§3.3）是最狠的一招，误读率断崖下降且零训练 |
| 3 | **典型距离/角度/光照？** 手持 30–80cm 正对，还是 2m 斜拍 + 金属货架反光 | 决定要不要 §4 的矫正与两遍读，以及要不要提分辨率 |

在拿到答案前，本方案按最可能的假设写：*印刷文本码 + 码表可枚举 + 手持 0.5m 左右正对*。

## 1. 分档总览

| 档 | 手段 | 训练 | 模型体积 | 何时用 |
|---|---|---|---|---|
| **L0** | `AVCaptureMetadataOutput` 读条码/二维码 | 无 | 0 | 码印成条码时首选，准确率碾压一切图像识别 |
| **L1** | Vision `VNRecognizeTextRequest` + 语法校验 | 无 | 0 | **起步就选这档**：本地、离线、实时 |
| **L2** | L1 + 图像前端（四点矫正 / ROI 放大 / 多帧投票） | 无 | 0 | L1 单帧召回不稳、斜拍、字太小 |
| **L3** | YOLO 只定位"标签牌" → 交给 L1 精读 | 小（1 类，300–500 框） | 10–12M | 杂乱背景、远景、画面里多张标签 |
| **L4** | 自训字符识别（SVTR/CRNN/ABINet） | 是（2k–10k 文本行） | 8–30M | L1/L2 在某类载体上 CER 仍 >8% 且码表不可枚举 |
| **L5** | 服务端 OCR / VLM 兜底 | 无 | 0 | 疑难件人工复核；有联网与隐私代价 |

推进原则：**L1 → 量化 → L2 → 量化 → 才谈 L3/L4**。跳级训练的收益通常不如"把标签拍正"。

## 2. L1 规格（可直接实施）

**采集**（已按实测调整）
- 会话预设 `.hd1920x1080`：远处小字首先输在像素上，1080p 给 Vision 的文本高度明显好于 720p；
  代价是单帧识别更慢，而帧闸本来就是"一帧没读完就丢新帧"，所以预览不会卡、只会降有效识别频率。
- 帧率：读码不需要 12fps，帧闸上限是 `iPhone/Code/ReadingConfig.swift` 的 `maxFrameRate`。
- **点对焦 + 双指变焦**（`CameraPageModel.focus(at:)` / `setZoom(_:)`）：
  小标签近拍时连续自动对焦会拉风箱，必须给 `focusPointOfInterest`；
  坐标换算交给 `AVCaptureVideoPreviewLayer.captureDevicePointConverted(fromLayerPoint:)`，
  不要自己写旋转公式（方向一改就错）。曝光点位设了但模式保持 `.continuousAutoExposure`，
  否则每次点对焦点画面会跳一下亮度。
- 物理限制：主摄最近对焦距离约 10cm，贴得更近**任何软件都救不了** —— 要么退开，要么数码变焦；
  真要贴脸读，得换超广角做微距（另一条镜头路线，未接）。

**Vision 请求参数**
已实现（`iPhone/Code/VisionTextCodeReader.swift`）：

```
recognitionLanguages      = ["en-US"]      // 码面只有大写拉丁字母 + 数字，加 zh-Hans 只会增加误召与耗时
recognitionLevel          = .accurate      // 库位码字小笔画近，.fast 漏读明显
usesLanguageCorrection    = false          // ★ 字母数字码必须关，否则 C3 会被"纠"成词
revision                  = 不写死          // Vision 默认用当前系统支持的最新版（iOS 18+ 即 revision3）
                                          // 头文件里 revision1/2 常量在 iOS 18 已标 deprecated
```
> 实测 SDK（iOS 27）里 `supportedRecognitionLanguages()` 是**实例方法**、
> 且没有 `automaticallyUsesImageEnhancements` 这个属性 —— 本表按真实签名写，别照抄旧博客。

**候选打分**（不取 top1，取"语法最自洽"）
```
score = 平均字符置信度 × 语法命中权重 − 归一化编辑距离 × 距离权重
```
- 每条 observation 取 `topCandidates(3)`，逐个过 §3 的校验器；
- 完全不符合语法的候选直接丢弃（宁可"没读到"，不可"读错"）。

**稳定判定（去抖）**
- 连续 **N=3 帧**得到同一合法结果才 fire：框变绿 + 触觉 + 大字显示；
- fire 后 800ms 冷却，避免同一标签重复触发；
- 连续 2s 未 fire → 出引导文案（"靠近一点 / 正对标签 / 避开反光"）+ 手动输入入口。

**必须盯的三个指标**（定义见 §6）：**误读率**（最高优先级）、首次成功时间 TTF、单帧耗时。

## 3. 语法与校验设计（这里省掉一半训练）

### 3.1 文法
以 `B2-4-2073` 为例：`货架-层-尾号`（早期口头例子 `C3-4-4483` 同形，都吃）
```
^[A-Z][0-9]-[0-9]{1,2}-[0-9]{1,4}$
```
→ 拆成**逐位字符集**：位置 0 只允许 `A-Z`，位置 1 只允许 `0-9`，位置 3 起只允许 `0-9`。
字符集本身就把一大半 OCR 错误挡在门外。收紧或放宽只改 `CodeGrammar.segments` 一处。

**两条已落地的保守规则**（都是"宁可不出，不出错"的具体化）：
1. **解释唯一才修正**：某位的混淆候选在该位字符集下只剩一个时才采纳
   （`44S6`→`4456` ✓；数字位上的 `0` 可能是 O/D/Q → 不猜，直接判读不出）。
2. **不擅自重新切分**：OCR 给了分隔符就尊重它的切分，只有分隔符被整个吞掉时才枚举切分。
   否则 `C-2-44567` 会被"救"成 `C-24-4567` —— 那是**改了值**，比读不出恶劣得多
   （这条是单测抓出来的，见 `Tests/CodeGrammarTests.swift`）。

### 3.2 混淆修正（按位置生效）
常见 OCR 混淆对：`O↔0`、`I↔1`、`L↔1`、`B↔8`、`S↔5`、`Z↔2`、`G↔6`、`D↔0`、`V↔U`。
修正只在**该位置字符集允许**时进行；一个位置只能换成一个字符时直接换，多个候选时按置信度加权。

### 3.3 白名单最近邻 ★ 优先做这个
如果合法码可枚举（你们系统里的库位号总数有限，通常几百到几万）：
- 端侧存一份码表（几 KB–几百 KB，SQLite/集合都行，AimFind 沿用工程约定即可）；
- 对识别结果做 **编辑距离 ≤1（可加权到混淆对的替换距离 = 0.5）** 的最近邻匹配；
- 唯一命中即采纳，多命中则要求更高置信度或直接判"不确定"。

这一步能把误读率压到 **<0.1%**，是比换模型、比训练有效得多的手段。

### 3.4 校验位（若能改上游）
如果码是新打的，说服上游加一位模校验（模 36 / Luhn 变体）：**误读率可以趋近 0**，
因为任意单字符错误都能被检出。这是"改一次规则，永久免疫"的选项。

## 4. L2：不训练就能拿到的增益

按性价比排序：
1. **四点矫正**：Vision 的 `orientationCorrection` + `boundingBox` 只是矩形；对斜贴标签，
   用检测到的文本框四角（或让 YOLO 出四角）做 homography 拉平后再识别 —— 斜拍场景提升最大。
2. **ROI 放大两遍读**：粗检拿到文本框 → 裁剪 → 放大 2–3× → 再识别一次。远距/小字首选。
3. **多帧投票**：同一标签连续多帧结果的加权多数表决（比单帧取最高置信度稳）。
4. **图像预处理**：自适应阈值二值化 / CLAHE 提对比 / 高光抑制（金属反光）；
   Core Image 滤镜链就够，别上 GAN 超分（延迟不值）。
5. **对焦与曝光锁**：手动 `focusMode = .autoFocus` + 限制曝光，避免自动对焦在反光上来回呼吸。

## 5. 什么时候真的需要训练（判据先行）

**先建基线**：拍 30–50 张真实作业场景（覆盖反光/斜角/远距/脏污），跑 L1（+L2 中已实现项），
统计 CER（字符错误率）与误读率。**没有这个数字就不要决定训练。**

触发训练的条件（同时满足才动手）：
- 某一类载体的 CER 持续 >8%，**且**
- 码表不可枚举 / 白名单救不回来，**且**
- §4 的矫正+两遍读已经试过并确认无效。

### 路线对比

| 路线 | 是什么 | 数据量 | 训练成本 | 体积 | 延迟 | 许可证 | 失败模式 |
|---|---|---|---|---|---|---|---|
| **A 字符识别** SVTR/CRNN/ABINet（PP-OCR 生态，Apache-2.0） | 文本行图 → 字符串，不检测只认字 | 2k–10k 行（合成 + 少量真实微调） | 单机数小时 | 8–30M | 20–60ms | Apache-2.0 | 域外字体/极端模糊掉点快；要自己接检测 |
| **B YOLO 当定位器** | 只训 1 类"标签牌"框，把 §2/§4 精读限制在 ROI 内 | 300–500 框 | 1 小时内 | 6–12M | 5–15ms | **AGPL-3.0**（ultralytics）；或换 Apache-2.0 的 YOLOX/NanoDet | 只解决"在哪"，不解决"认不出" |
| **C 模板/角点矫正** | 标签版式固定 → 已知四角做 homography | 0（标定即可） | 0 | 0 | <5ms | — | 版式一变就失效 |
| **D 传统 CV** | 连通域切字符 + 小分类器 | 每字符 50–200 张 | 分钟级 | <2M | <10ms | — | 字符粘连/断裂直接崩 |

**推荐顺序：C → B → A**。C 免费且常够；B 只补"找不到"，不补"认不出"；A 是最后手段。
> **现状**：路线 A/B 曾有过一份 CoreML + YOLO 实现（解码、letterbox 反映射、NMS、三种导出布局自适应，
> 带 8 条单测），**已删除** —— 它要解决的问题尚未被证明存在，而本节 §4 的零成本手段一个都没试。
> 实现留在 git 历史 `1ea5f92`（`iPhone/Detection/`），要接回来看这份文档即可。
> 当时验证过的输出契约（`[attrs, anchors]` / letterbox 像素空间）对 B 依然适用，
A 路线要单独处理：**Core ML 的文本识别模型输入是变长宽度**，导出时定长 pad 到 32×W 或用
`VNCoreMLRequest` 之外的 `MLModel` 直调；类名表（字符集）必须走自定义 metadata，
这是历史实现里唯一没覆盖的口子（当年写在 `VisionYoloDetector.loadModel`，删除前逻辑见 git `1ea5f92`）。

## 6. 数据与标注规范（走 A/B 时）

- **采集**：每个物理标签 15–20 角度 × 3 光照 × 2 距离；必须含反光/脏污/局部遮挡样本；
  跨场景划分 train/val —— **同一张实体标签不能同时出现在 train 和 val**（这是最常见的数据泄漏）。
- **标注**：文本行框 + 转写内容；工具 PPOCRLabel（A）/ LabelImg·CVAT（B）。
  B 路线只要一个类别，标注量极小。
- **合成增强**（A 的主力）：字体 × 透视 × 高斯模糊 × JPEG 压缩 × 低照度渲染管线，
  先合成预训练、再真实数据微调；真实数据占比不用高，但**必须来自现场**。
- **验收**：按场景分桶报 CER/误读率（反光桶、斜角桶、远距桶），**只看总体平均会骗人**。

## 7. 接入现有框架的形状（不改已验证的部分）

```
CameraPageModel（会话 + 帧闸 + 发布）        ← 复用，不动
   ├─ Detector   → YOLO 检测框（L3 的定位器 / 现有 COCO 能力）
   └─ CodeReader → ReadCode{value, confidence, box}   ← 新增，与 Detector 平级
        VisionTextCodeReader（L1/L2）· SVTRCodeReader（L4）
   ▼
CodeGrammar（纯函数：逐位字符集 + 混淆修正 + 白名单最近邻）  ← 全单测，不碰相机
   ▼
DetectionOverlay 复用（坐标仍是归一化 box → ViewportMapper）；命中后框变绿 + 触觉 + 大字
```
模型放置与查找链沿用 `Resources/Models/` + `mlmodelc → mlpackage → mlmodel`（含运行时编译兜底）。

## 8. 验收指标（建议门槛）

| 指标 | 定义 | L1 目标 | 白名单模式目标 |
|---|---|---|---|
| **误读率** | 输出错误码 / 总输出数（**最高优先级**，宁可不出） | <1% | **<0.1%** |
| 拒读率 | 未出结果 / 应出结果 | 可接受高（换误读率） | — |
| TTF | 对准到 fire 的时间 | <1.5s | <1.2s |
| 单帧耗时 | 检测+识别+校验 | <80ms（≤8fps） | <80ms |
| 热/电 | 连续 60s 取景 | 不触发降频掉帧 | — |

回归资产：录 **20 段现场视频**当固定评测集（覆盖六类场景），每次改动跑一遍出上面五个数；
`CodeGrammar` 的混淆/边界/非法串全部写单测（不需要相机，纯函数）。

### 3.45 自动合焦到识别出的位置（已实现，`iPhone/Code/AutoFocus.swift`）
读到码之后，等效于手指在那一点一下：**框中心 → 视口坐标 → 设备对焦坐标 → `focusPointOfInterest`**。

- 坐标换算不自己写旋转公式：先过 `ViewportMapper`（与画框**同一个**映射，保证"框在哪，焦点就在哪"），
  再过 `AVCaptureVideoPreviewLayer.captureDevicePointConverted(fromLayerPoint:)`；
- 不逐帧重锁 AF：中心移动 <6% 忽略、两次合焦间隔 <0.7s 忽略（反复重锁既费电又让画面抽动）；
- 每次自动合焦都在同一位置画出准星，用户看得见它对焦在哪。

> 曾按"自动变焦"实现过一版（`videoZoomFactor` 闭环），已撤回：数码变焦只能绕画面中心，
> 而需求是合焦到识别点。手动双指变焦保留。

### 3.5 稳定判定（已实现）
- 连续 **3 帧**读到同一个码才锁定（`CameraPageModel.stableHits`）：框变绿 + 大字 + 成功触觉反馈；
- 连续 **4 帧**读不到才放开（`missesToRelease`）：偶发丢帧不该清空已锁定的结果；
- 同一条文本行的 top-3 候选按 `置信度 − 0.25 × 修正位数` 打分择优，对外报的仍是 OCR 原始置信度。

## 9. 一周到"能用"的顺序

1. **半天**：确认 §0 三问。若是条码/二维码 → L0 结束。
2. **1 天**：L1 打通 —— ✅ **已完成**（Vision + §3.1/3.2 校验 + 连续 3 帧去抖，
   纯函数层 26 个测试全绿）。剩：拍 30 张脱敏样本出 CER/误读率基线（要真机 + 真码）。
3. **半天**：拿到码表就上 §3.3 白名单最近邻。**多数项目到这就结案了。**
4. **1–2 天**：不够就加 §4 的矫正 + 两遍读 + 多帧投票，重测基线。
5. **再不够**：才动训练，顺序 C → B → A（§5）。

## 11. 已实现（2026-10-27，L1 + §3.5 稳定判定）

脱敏样本把 §3.1 的假设改了两处，现在工程里跑的是这个版本：

| 项 | 计划里的写法 | 实际（按真实标签） |
|---|---|---|
| 段1 货架 | 1 位大写字母 | **1–2 位字母或数字**（`38-1-6760` 与 `C-2-4456` 都要吃） |
| 段3 尾号 | 1–4 位数字 | **恰好 4 位**（定长才是区分日期/价格/距离的依据） |
| 搜索键 | 完整码 | **尾号优先**：远处只有那 4 位大字读得到；完整码作为二次确认 |

代码落点：`iPhone/Code/`（`CodeGrammar` 语法、`TargetMatcher` 目标匹配、`PositionHint` 方位、
`TextReader`/`VisionTextReader` 只回原文行）。分工是 reader 不认识语义、语义层不碰相机，
所以 36 个纯逻辑测试全部离线跑（`docs/BUILD.md §4` 的 SwiftPM 办法）。

实现过程中被测试/样本推翻的三件事，都写进了保守规则：
- 运单号 `YT8747063366760` 末尾就是 `6760` → **禁止子串匹配**，按 token 边界切；
- 货架条上的 `1-4-XXXX` 占位符 → `X` 不在混淆表里，天然读不成码（否则会当成 1-4-某号）；
- 早期实现会把 `C-2-44567` 重新切分成 `C-24-4567` → **给了分隔符就尊重切分**（那是改值，不是纠错）。

下一步（还没做）：真机对真标签的 CER/误读率基线；两阶段（YOLO 先定位标签牌 → 精读）；
码表白名单最近邻（§3.3，拿到码表后是压误读率最有效的一招）。

## 12. 取件码的真实来源（2026-10-27 补充，改变了输入方式）

用户给了两张截图，来源是**驿站/快递柜的取件通知**，不是仓库标签：

```
【示例驿站】您有包裹已到达文苑路店，取件码为C5-5-7225，地址:示例路1号小区2区-3号楼103室
快件已在【示例区文苑路店】暂放，…，取件码 B2-4-2073
```

由此确定的文法：`货架(1–2 位字母或数字) - 层(1–2 位数字) - 尾号(恰好 4 位数字)`，例如 `B2-4-2073`、`C5-2-9914`。

**一条被样本推翻的规则**：原先 `tokens()` 用 `.alphanumerics.inverted` 切分，而中文在 Unicode 里算字母数字
—— 于是「取件码为C5-5-7225」会被切成 `码为C5` 这种 token，**码直接丢掉**。现在分隔规则改成
「只有 ASCII 字母数字算字符」，中文一律是分隔符。副作用是好的：`YT8747063366760` 仍是单个 token，
不会因为结尾是 6760 而误命中。

## 13. 导入 → 标签 → 多目标同找（已实现）

```
相册截图(PhotosPicker，无需相册权限) → VisionTextReader.read(cgImage:) 文本行
   → CodeInbox.extract(lines:)  只要「带前缀的完整码」+ corrections == 0，去重、上限 12
   → 标签墙（滑动删除）→ 打开相机时整组交给 CameraPage
   → TargetMatcher.locate(hits, targets:) 一行文本可命中多个标签中的任一个
   → 每个标签各自计「连续 3 帧」才记找到；顶部 k/N 进度；找到的标签沉底、框加淡填充
   → 合焦只找**还没找到**的目标；全部找到后显示「全部找到」并停止移动镜头
```

导入这一侧刻意**比实时更严**：只收完整码、拒绝任何需要修正的读法（`C5-5-722O` 不收）——
标签列表里出现一个错码，会让人在货架前白找半天；漏一个则只要再传一次截图。

## 14. 两个现场体验补丁（已实现）

**屏幕常亮**：相机页 `.onAppear` 置 `UIApplication.shared.isIdleTimerDisabled = true`，
`.onDisappear` 归还原状。在货架前扫码时锁屏等于中断搜索；离开页面就把控制权交还系统，
不做全局常亮。

**货架清点 `ShelfCensus`（把"没扫到"和"这里没有"分开）**：统计画面里出现的**所有完整取件码**
（不限于目标），持续 2.5s 没有新码出现且已见 ≥3 件 → 判定"这层 N 件里没有你要的，换一层试试"；
否则显示"已扫到 N 件…"。要点：
- 计数靠每帧重新登记刷新时间戳，TTL 4s —— 镜头移开一段距离后旧码自然过期，不会把上一层算进来；
- 出现新码就把结论收回，重新进入"正在扫"；
- 只看到 1–2 件时**不下结论**（可能只是扫到边角），这条是被单测钉住的（`Tests/ShelfCensusTests.swift`）。
